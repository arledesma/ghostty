  <name>Task 1: Fix URL opening to avoid MTA/STA crash</name>
  <files>src/apprt/windows/App.zig</files>
  <action>
The crash occurs because ShellExecuteW internally loads shell extensions via COM, which require STA (single-threaded apartment). But the app initializes COM with RO_INIT_MULTITHREADED (MTA).

**Fix approach: Return false from performAction(.open_url) to use the core fallback.**

The core Surface.zig `openUrl` method checks the return value of `performAction(.open_url)`. If the apprt returns `false`, the core falls back to `internal_os.open(url)` which on Windows uses `std.process.Child` to spawn a process. This avoids ShellExecuteW entirely.

In App.zig, find the `.open_url` handler (around line 1567-1579). Replace the entire block:

From:
```zig
.open_url => {
    const url = value.url;
    if (url.len == 0) return true;

    // Convert UTF-8 URL to null-terminated UTF-16.
    var wide_buf: [2048]u16 = undefined;
    const wide_len = std.unicode.utf8ToUtf16Le(&wide_buf, url) catch return false;
    if (wide_len >= wide_buf.len) return false;
    wide_buf[wide_len] = 0;
    const url_wide: LPCWSTR = @ptrCast(&wide_buf);

    _ = ShellExecuteW(null, null, url_wide, null, null, SW_SHOW);
    return true;
},
```

To:
```zig
.open_url => {
    // Return false so core falls back to internal_os.open().
    // ShellExecuteW requires STA COM but we initialize MTA for WinRT.
    // The core fallback spawns a child process which avoids the conflict.
    return false;
},
```

This is the simplest and most robust fix. The ShellExecuteW extern declaration and SW_SHOW constant can remain (they may be used elsewhere or in the future).

**What NOT to do:**
- Do NOT spawn a dedicated STA thread -- unnecessary complexity when the core fallback exists.
- Do NOT change the COM initialization to STA -- WinRT activation requires MTA (RoInitialize).
- Do NOT use `cmd /c start` -- the core fallback already handles cross-platform URL opening correctly.

<task type="auto">
  <name>Task 2: Fix defaultTermioEnv to inherit system environment</name>
  <files>src/apprt/windows/Surface.zig</files>
  <action>
The current `defaultTermioEnv` returns an empty `EnvMap`. This means child processes (pwsh.exe, powershell.exe) receive only the few Ghostty-specific env vars set in Exec.zig, missing critical Windows system variables like SYSTEMROOT, USERPROFILE, APPDATA, PATH, etc. PowerShell cannot start without these.

**Fix: Call `internal_os.getEnvMap` to inherit the system environment, matching GTK and embedded apprt behavior.**

In Surface.zig, first add the import for internal_os. Check if it already exists at the top of the file. If not, add:
```zig
const internal_os = @import("../../os/main.zig");
```

Then replace `defaultTermioEnv` (lines 264-268):

From:
```zig
/// Return the default termio environment. ConPTY inherits
/// the process environment, so return an empty map.
pub fn defaultTermioEnv(self: *Surface) !std.process.EnvMap {
    return std.process.EnvMap.init(self.app.alloc);
}
```

To:
```zig
/// Return the default termio environment. We inherit the system
/// environment so child processes receive SYSTEMROOT, PATH, etc.
/// Exec.zig then layers Ghostty-specific vars (TERM, COLORTERM, etc.)
/// on top.
pub fn defaultTermioEnv(self: *Surface) !std.process.EnvMap {
    return internal_os.getEnvMap(self.app.alloc);
}
```

This matches how the GTK apprt (gtk/class/surface.zig line 1530) and embedded apprt (embedded.zig line 929) both call `internal_os.getEnvMap`. The old comment about "ConPTY inherits" was incorrect -- ConPTY inherits the parent's *console* environment, but CreateProcessW with an explicit env block (non-null lpEnvironment) overrides inheritance entirely.

**Bell note:** The bell code path (MessageBeep + FlashWindow) is already correctly wired. The bell issue from UAT test 13 is likely caused by: (a) ConPTY intercepting BEL in cmd.exe, or (b) the shell itself not emitting BEL because it couldn't start properly (the env fix may resolve the pwsh/powershell issues, allowing bell to work). No code changes needed for bell itself -- fixing the environment is the actionable fix.

**What NOT to do:**
- Do NOT modify Exec.zig's cmd.exe /C wrapping -- while suboptimal, it works for both cmd.exe and PowerShell when the environment is correct. The wrapping issue is a separate concern.
- Do NOT modify the bell handler -- the code path is correctly implemented.
